# SDD Workflow v21

> Active. One implementation authority implements, validates, repairs and records evidence; `spec-test` certifies.

## Public commands

| Command | Purpose |
|---|---|
| `/spec-plan` | Author roadmap work before the pipeline |
| `/spec-pipe <N>` | Orchestrate new → unified implementation/repair → certification |
| `/spec-new <N>` | Validate and author requirements, design, tasks |
| `/spec-implement <N>` | Implement, validate promptly, repair, and persist verified task facts |
| `/spec-test <N>` | Certify; if repairable, hand failures to the same implementation executor within the running pipe |
| `/spec-debug <N>` | Read-only evidence, next action and state |

Roadmap progress is independent from test evidence. `audited` is never inferred from task checkmarks or code modifications. A non-certifying code-writing fallback is not an acceptable substitute for normal implementation.

## On validation failure

Provide the actual command, failing test, assertion, error location, and relevant sanitized stdout/stderr. Do not retry blindly. Compare progress using current code and validation evidence, not document hashes alone. If previous errors have been eliminated and a different test remains, the attempt is progressing.

## On interruption

Persist partial work and a safe next action. User cancellation is terminal for that invocation; an active/unresponsive runtime or unknown external side effect must not be replayed. Recover automatically when safe and within limits. The user does not have to reset a spec to address an ordinary failed test.

## Status

`planned` → `verified` → `in-progress` → `implemented` → `audited`. Operational `paused-resumable` is distinct from roadmap status and from certification. Treat existing v20 ledgers and records through tested compatibility logic; never rewrite history to manufacture completion.

## Safety and scope

Respect user permissions, confined paths, secret controls and budget ceilings. Do not delete valid code as a consequence of administrative reconciliation. Proof is generated by verification, not by LLM opinion. For detail see `sdd-contrato/sdd-base.txt` and `sdd-contrato/sdd-fluxo.md` after version activation.
